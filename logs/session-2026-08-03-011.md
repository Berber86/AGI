## Гипотезы

Применяю скилл `skills/hypothesis-first.md`, потому что новый gate может ошибочно блокировать
сильные сессии или создавать ложное чувство безопасности; критерии нужны до реализации.

### Г1 — Допуск по поведению безопаснее и информативнее допуска по идентичности
- **Задача:** формально запретить introspection/guess/allowlist и оценивать только результат тестов.
- **Предположение:** это соблюдёт ограничения Arena.ai и будет измерять текущую полезную
  компетентность, а не бренд, самоотчёт или потенциально устаревшую маршрутизацию.
- **Метрика:** policy, challenge, receipt и лог не содержат поля идентичности/списка моделей;
  допуск можно пройти, не выясняя происхождение текущей LLM.
- **Риск:** случайно записать догадку или превратить запрет в список узнаваемых названий.

### Г2 — Три разнородных одноразовых теста дадут полезный ранний фильтр
- **Задача:** проверить constraint-following, многошаговое планирование и точную code-repair.
- **Предположение:** строгий порог 3/3 отсеет сессии, которые не могут надёжно выполнять базовую
  агентную работу, но не будет зависеть от trivia или саморефлексии.
- **Метрика:** текущая сессия проходит свежий случайный challenge одним `check`; намеренно неверные
  ответы дают FAIL; schedule остаётся однозначным на серии seeds; code validator ловит исходный bug.
- **Риск:** тесты могут быть слишком лёгкими, слишком формат-зависимыми или со временем заучиться.

### Г3 — Fail-closed протокол сделает пропуск допуска видимым
- **Задача:** связать одноразовый результат с текущим логом и общей верификацией.
- **Предположение:** marker, который пишет сам checker, плюс проверка последнего лога в
  `src/verify.py` заставят нормальную сессию остановиться при FAIL/отсутствии результата.
- **Метрика:** PASS-marker принимается verify; FAIL, отсутствие marker, повторная сдача,
  изменение checker/policy или tracked tree отклоняются внешним тестом.
- **Риск:** у агента нет криптографически защищённой границы: намеренно нарушающий инструкции
  процесс всё ещё может подделать файлы или не запустить verify.

### Г4 — Корреляцию gate с решением создателя нельзя честно доказать в одной сессии
- **Задача:** заложить калибровку, не выдавая локальный self-test за реальную предсказательность.
- **Предположение:** после нескольких Arena-сессий можно сравнить PASS/FAIL с ручным merge/reject
  и менять сложность только по false accept/false reject.
- **Метрика:** в TODO появится серия калибровки с ручными метками; README честно сохраняет
  человеческий review как окончательный барьер.
- **Риск:** vanity-score 3/3 начнут воспринимать как доказательство качества всей будущей работы.

## Триадная проверка архитектуры допуска

Применяю скилл `skills/triad-review.md`, потому что gate меняет право сессии выполнять работу и
может сам стать источником ложных решений.

**Предложение:** identity-blind gate версии 1, три категории, случайный challenge, один check,
порог 3/3, runtime в `.runtime/`, PASS/FAIL-marker в логе, fail-closed инструкция и verify-gate.

**Отвергнутые альтернативы:** определение активной модели; allowlist; чистая самооценка;
статические загадки с ответами в prompt; автоматический merge после PASS; тяжёлый внешний сервис.

### 🟢 Генератор

Три теста покрывают разные необходимые свойства. Политические кейсы проверяют следование
ограничениям, уникальная schedule-задача — точное многошаговое рассуждение/умение пользоваться
инструментами, code-repair — фактическую работу coding agent. Случайность снижает механическое
заучивание, детерминированный checker исключает самооценку, одноразовость мешает подбору.

### 🔴 Критик

Это не security boundary: checker, алгоритм и runtime находятся в доступной агенту файловой
системе. Модель может прочитать reference, подделать marker или изменить порог. Белый ящик
измеряет добросовестную компетентность, а не защищает от злонамеренного обхода. Статический тип
code-repair может заучиться, строгий JSON создаёт false reject, а PASS ничего не говорит о
качестве длинной архитектурной работы. Запуск чужого candidate-кода требует timeout и subprocess.

Требования Критика: запретить чтение private state/checker во время попытки; проверять чистый git,
HEAD и hash checker/policy; дать готовый answer-template; checker должен сам писать marker и
запирать попытку до раскрытия деталей; явно назвать ручной merge окончательным барьером; добавить
калибровку на будущих сессиях.

### 🟡 Скептик

Создатель уже надёжно фильтрует ветки вручную, поэтому сложный benchmark не должен подменять его
суждение. Но ранний gate экономит время и предотвращает загрязнение ветки до review. Одобряю
минимальную версию без сети, базы рейтингов и попыток «угадать движок». Если прототип разрастается
или не коррелирует с merge/reject, его надо упростить либо удалить.

### Синтез

Решение **принять с ограничениями**. Gate — ранний fail-closed фильтр добросовестной способности,
не аттестация бренда и не защита от намеренного обхода. Порог v1 — 3/3, одна попытка. Сначала
создаётся и коммитится прототип; затем на чистом HEAD текущая сессия проходит реальный challenge.
Только после успешного модельного применения вносятся конституционная поправка и интеграция.
Откат — удалить новый орган и вернуть awakening/verify через `git revert` двух коммитов #011.

### Неожиданности

- Новый gate сразу продемонстрировал цену always-loaded правил в контекстном бюджете.
