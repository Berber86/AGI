# Эксперимент «Игра растёт вместе со сложностью»

## Суть эксперимента

Создаётся игра, которая **начинается с уровня 4/10 и постепенно растёт до 10/10**. С каждым
новым уровнем сложности растёт число сессий разработки и — главное — **число и специализация
разработчиков-агентов**.

**Ключевой принцип:** сколько сложность `X/10`, столько и сессий разработки. Каждая сессия —
это отдельная **gamedev-роль** со строго своей зоной ответственности, выполняемая по 4-этапному циклу.

> ⚠️ **Важно:** мы стартуем сразу с **4/10 со всем хардкором**. Это означает, что первый уровень,
> который мы делаем, — **4/10 по сложности геймплея И по производственному качеству**.
> Никаких «детских браузерок» — начинаем с полноценной инди-игры среднего уровня.

## Шкала качества (производственный бар)

`X/10` задаёт **два независимых параметра**, оба должны быть выполнены на своём уровне:

1. **Хардкор геймплея** — насколько сложна и глубока игра (правила, стратегия, цена ошибки).
2. **Производственное качество (продакшен)** — насколько профессионально сделана игра.

Ориентиры производственного бара:

| Уровень | Что это примерно |
|--------:|------------------|
| 1/10 | Детская браузерка: минимум, всё на коленке |
| 3/10 | Аккуратная инди-игра: цельный стиль, понятный UX, отлаженный баланс |
| 4/10 | **Стартовая точка**: глубокая инди-игра с модульным кодом, качественным звуком и богатыми механиками |
| 5/10 | Полированная инди: проработанный арт, звук, уровни, вариативность |
| 7/10 | «Двойной-А»: высокое качество арта/звука, насыщенный контент |
| 10/10 | **AAA-проект**: высочайший продакшен во всех дисциплинах |

Каждый следующий уровень поднимает **обе** шкалы: и хардкор, и продакшен.

---

## 🏗️ Обязательное правило: Модульная структура игры

Игра **не должна быть монолитным HTML-файлом**. Создаваемая игра обязана иметь **модульную структуру**:
- `index.html` — точка входа и каркас приложения (совместимо с Vercel);
- отдельные файлы стилей (например, `css/style.css`);
- отдельные JS-модули по логическим слоям (например, `js/data.js`, `js/engine.js`, `js/ui.js`, `js/audio.js` и др.).
Это гарантирует масштабируемость и чистоту архитектуры от 4/10 до 10/10.

---

## 🔄 Главное правило ролей: ТОТАЛЬНЫЙ ПЕРЕСБОР

**Каждая роль пересобирает свою область с нуля под производственный бар своего уровня —
а не «добавляет чуть-чуть к новым механикам».**

- **Графический дизайнер** уровня `N` обязан **заново оформить ВСЮ игру** (все экраны, все юниты,
  все иконки, весь UI, анимации, стиль) до производственного качества уровня `N`.
- То же касается **каждой роли** в своей области: геймдизайнер перепроектирует всю игру до нового
  хардкора, звуковой дизайнер озвучивает всё, дизайнер уровней перестраивает всю структуру и т.д.
- Итог каждого уровня — **цельная игра уровня `N` целиком**, а не «старая игра + несколько новых фич».

---

## 🛠️ Новый 4-этапный цикл каждой сессии (А / Б / В / Г)

Каждая сессия (для каждой роли) теперь строго следует **4-этапному жизненному циклу**:

### А) Старт роли
Роль выполняет свою проектную работу (дизайн, визуал, аудио, баланс и т.д.) в рамках своей компетенции, формируя архитектуру и решения для уровня `N/10`.

### Б) Старт программиста для роли
Программист реализует код вклада роли в модульной структуре проекта, интегрируя новые механики, стили или аудио-движок.

### В) Старт Критика (3 проблемы проекта + 4 варианта решения)
Подключается **Критик**, который оценивает **весь проект целиком** (а не только узкую область текущей роли), выявляет **3 главные проблемы / точки роста** текущей игры и задаёт пользователю **ровно 3 вопроса** (по одному на каждую проблему).
Для каждого вопроса Критик предлагает:
- **Варианты A, B, C:** Три конструктивных способа решения выявленной проблемы;
- **Вариант D:** «Оставить так» (сохранить текущую реализацию без изменений).

### Г) Программист вносит коррективы и исправления
На основе ответов пользователя на вопросы Критика программист вносит итоговые исправления, доработки или оптимизации, проводит автоматические тесты и сдаёт сессию.

## Как устроены уровни

**Стартовая точка эксперимента — уровень 4/10.** Далее команда растёт накопительно до 10/10.

| Уровень | Сессий | Команда (роли) |
|--------:|:------:|----------------|
| **4/10** | 4 | Геймдизайнер · Графический дизайнер · Балансир · Звуковой дизайнер |
| 5/10 | 5 | + Дизайнер уровней |
| 6/10 | 6 | + QA-тестировщик |
| 7/10 | 7 | + Нарративный дизайнер |
| 8/10 | 8 | + Системный дизайнер |
| 9/10 | 9 | + Дизайнер прогрессии |
| 10/10 | 10 | + Техлид / Продюсер |

Полное описание ролей, их зон ответственности и порядка сессий — в **`docs/TEAMS.md`**.

## Порядок действий агента при старте сессии

1. **Прочитай `README.md`** — усвой правила 4-этапного цикла и модульности.
2. **Прочитай `docs/TEAMS.md`** — определи свой уровень сложности и свою роль.
3. **Прочитай `docs/STATE.md`** — узнай текущее состояние.
4. **Прочитай записи прошлых сессий** в `records/` — учти принятые решения.
5. **Этап А (Роль):** Выполни проектную работу своей роли.
6. **Этап Б (Программист):** Реализуй модульный код для вклада роли.
7. **Этап В (Критик):** Оцени весь проект, выяви 3 проблемы и задай пользователю 3 вопроса с вариантами ответов (A, B, C + D: "оставить так"). Запиши в журнал.
8. **Этап Г (Коррективы программиста):** Внеси исправления по ответам пользователя, проверь стабильность автотестами.
9. **Сдай сессию:**
   - обнови `docs/STATE.md`;
   - сохрани журнал в `records/<уровень>/<роль>.md`;
   - закоммить изменения с понятным сообщением.

## Структура репозитория

```
README.md            — эта инструкция (читай первой)
docs/
  TEAMS.md           — реестр команд и ролей для уровней 4-10
  STATE.md           — текущее состояние эксперимента
records/
  README.md          — правила ведения журналов сессий
  _template.md       — шаблон записи сессии (этапы А/Б/В/Г)
  <уровень>/<роль>.md — журналы конкретных сессий
index.html           — точка входа игры (для Vercel / браузера)
css/                 — стили игры
js/                  — модули игровой логики и движка
```
