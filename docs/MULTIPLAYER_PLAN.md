# Архитектурный План Мультиплеера (MULTIPLAYER_PLAN.md)

## 1. Концепция и Подходы к Реализации

Для тактической игры с пошаговой/автотактической механикой боя «Механизм Цивилизации» рассматриваются две основные архитектурные модели:

### Модель А: Асинхронный PvP (Asynchronous Defend & Raid) — *Рекомендуемый выбор*
- **Принцип:** Игрок формирует и выгружает свой «Оборонительный Гарнизон» (3 чемпиона, экипированные шестерни, боевые позиции на сетке 10x20). Другие игроки подбираются по рангу MMR и нападают на этот сохраненный сетап.
- **Преимущества:**
  - Идеально для мобильного/веб формата (нет проблем с лагами, пингом и дисконнектами).
  - 100% защита от читерства: симуляция боя `simulateFight` запускается изолированно на сервере в среде Node.js / Go / Rust.
  - Нулевая зависимость от одновременного онлайна двух игроков.
- **Недостатки:**
  - Отсутствие синхронного взаимодействия в реальном времени.

### Модель Б: Синхронный Real-time PvP (Lobby & Lock-in Phases)
- **Принцип:** Два игрока подключаются через WebSocket к единой комнате. Фаза подготовки (30 секунд) на расстановку и тактику, затем одновременный старт симуляции с синхронизацией тиков или передачей зерна (seed).
- **Преимущества:**
  - Ощущение живого соперника и соревновательного напряжения.
- **Недостатки:**
  - Сложность обработки разрывов связи и тайм-аутов ходов.
  - Требует инфраструктуры постоянных соединений (WebSockets / WebRTC).

## 3. Дорожная Карта Интеграции

1. **Этап M1 (Текущий):** Чистый изоморфный движок (выполнен в Фазе 0). Детерминированный PRNG с фиксированным `seed`.
2. **Этап M2:** Простой REST API микросервис на Fastify/Node.js с вызовом `simulateFight`.
3. **Этап M3:** Таблица лидеров (Leaderboard) и асинхронный поиск соперников по MMR.
4. **Этап M4:** Система реплеев (хранение только массива `[armyA, armyB, seed]`, бой воспроизводится клиентом 1:1 детерминированно).
