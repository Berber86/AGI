# План мультиплеера (исследование, не имплементация)

> Фаза 5 сознательно ограничена архитектурной подготовкой. Этот документ — анализ
> вариантов и рекомендация. Код сервера не пишется до явного запроса.

## Что уже готово (заслуга Фаз 0–3)

- **Движок изолирован**: `src/engine/**` — чистые функции, вся случайность через
  `Rng(seed)`, ноль DOM/localStorage/React. Пурити-гвард (`tests/engine/purity.test.ts`)
  падает при любом нарушении.
- **Симуляция самодостаточна**: `BattleSim`/`simulateFight` принимают массивы
  `ComputedUnit` — их можно собрать где угодно (контракт: `docs/API_CONTRACT.md`,
  код: `src/engine/remote/contract.ts`).
- **Бой не персистится на клиенте** (D-22) — серверный источник правды ничего не ломает.

## Вариант A — асинхронные бои (Clash of Clans / идл-арены). ✅ РЕКОМЕНДУЕТСЯ

Игрок собирает защиту (или «призрачную» копию своей атаки), сервер считает бои офлайн.

```
Игрок A атакует → клиент присылает состав атаки (BattleSimulateRequest)
Сервер: валидация → computeUnit → simulateFight(seed) → результат + events
Сервер пишет итог в БД (win/loss/лут), A смотрит реплей через events
Защитник B видит лог обороны у себя; его ввода в моменте не требуется
```

**Почему первым шагом:**
1. Бой уже автотактический — «защита без игрока» органична (в отличие от шутеров).
2. Momentum-тактики — единственный ручной слой. Для защитника он заменяется
   скриптом-приоритетом («при духе 4 — Ярость»), который сериализуется в запрос.
3. Не нужен ни матчмейкинг по пингу, ни синхронизация времени, ни античит реального
   времени. `MOMENTUM_RULES` уже в движке — скрипт проверяется тем же кодом.
4. Дешёвая инфраструктура: stateless-эндпоинт + одна таблица результатов.

**Минусы:** нет «живого» соперничества; рейтинг легко фармить → нужен матчмейкинг по ELO
и лимиты попыток.

**Стек (рекомендация):** Node + Fastify (тот же TS, тот же модуль движка — код движка
копируется сборкой монорепо или публикуется как пакет `@cog/empires-engine`); БД —
Postgres (результаты, рейтинги) + объектное хранилище для events (или сжатые JSON).

## Вариант B — синхронный PvP с одновременными ходами

Оба игрока вводят Momentum-решения на чекпоинтах; раунды считаются после того,
как оба выбрали (или таймаут 5 сек → автобой).

```
WS-комната на бой → сервер рассылает кадры раунда → ждёт выборы на чекпоинтах
Раунд N считается только когда: оба выбрали ИЛИ таймаут
```

**Плюсы:** настоящее соревнование, «дуэли умов» на тактиках.
**Минусы:** нужен сервер комнат и таймеры; нетривиальный реконнект; UX-сложность
(ожидание соперника на каждом чекпоинте). Движок уже умеет: `BattleSim.step()`
позволяет класть выбор тактики между шагами — но дисциплина таймаутов и
воспроизведение «фантомных» раундов — новая работа.

## Вариант C — realtime-контроль юнитов

Прямое управление в моменте. **Отклонён**: противоречит дизайн-решению №6
(автотактика, решения только в стартовой расстановке и Momentum-точках).

## Эволюция противодействия читерству

| Уровень | Механизм |
|---|---|
| Уже есть | В контракте нет статов — сервер сам считает из справочников |
| A | Сервер генерирует seed для PvE-наград; лимиты попыток/дня |
| A+ | Реплей-верификация: спорные рейтинги пересчитываются из events |
| B | Сервер-таймауты, подпись сессии, дедупликация выборов |

## Миграция без слома PvE

1. Вынести константы баланса в публикуемый пакет (общий для клиента и сервера).
2. Поднять `POST /battle/simulate` (Вариант A) — PvE остаётся локальным, кампания не меняется.
3. Рейтинговые стычки через сервер; локальная «Стычка» помечается `unranked`.
4. Только потом — WS-комнаты (Вариант B), если будет запрос.
