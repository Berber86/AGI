# Политика допуска сессии по наблюдаемой компетентности

Версия: 1 (2026-08-03, сессия #011)

## Назначение

Среда Arena.ai может назначать разным сессиям LLM с неодинаковой фактической способностью.
Эта политика вводит ранний capability admission: до содержательной работы сессия решает свежий
одноразовый challenge, получает детерминированный PASS/FAIL и продолжает работу только после PASS.

Допуск оценивает **поведение в этой сессии**, а не происхождение или название модели.

## Неприкосновенный identity-blind инвариант

Во время допуска и последующей работы запрещено:

- выяснять активную модель через metadata, скрытые переменные, самоопрос или косвенные признаки;
- угадывать, подтверждать либо записывать идентичность активной модели;
- вести allowlist/denylist названий и выбирать право на работу по такому списку;
- добавлять в challenge, answer, receipt или лог поле с идентичностью/догадкой;
- обходить запрет эвфемизмом, если запись всё равно однозначно раскрывает активную модель.

Разрешено говорить только о наблюдаемом результате: версия протокола, challenge id, категории,
балл и PASS/FAIL. Название платформы и общий термин LLM не являются идентичностью модели.

## Модель угроз и честное ограничение

Это **не криптографическая граница**. Агент имеет доступ к репозиторию и теоретически может
прочитать checker, private runtime или подделать marker. Gate предназначен для добросовестной,
но потенциально слабой сессии: проверить, способна ли она следовать процедуре, решать задачу и
получать внешний сигнал. Ручное решение создателя о merge остаётся окончательным барьером.

Намеренное чтение `src/admission.py`, тестов или `state.json` после выдачи challenge и до сдачи
считается обходом, а не прохождением. До `issue` архитектурное чтение checker разрешено только
в отдельной сессии разработки самого gate.

## Когда запускать

После чтения bounded core, но **до** task-directed retrieval, постановки гипотез новой задачи и
любых tracked-изменений. Допустимы только созданный лог сессии и файлы в игнорируемой `.runtime/`.

## Протокол одной попытки

1. Убедиться, что текущий лог зарегистрирован, а tracked tree и index чисты.
2. Выдать challenge:

   ```bash
   python src/admission.py issue --session-log logs/session-YYYY-MM-DD-NNN.md
   ```

3. После `issue` читать только:
   - `.runtime/admission/<session>/challenge.md`;
   - `.runtime/admission/<session>/answer-template.json`;
   - `.runtime/admission/<session>/candidate.py`;
   - эту policy, если нужна проверка процедуры.
4. Не читать `state.json`, `src/admission.py` или `tests/` и не менять tracked-файлы.
5. Решить challenge. Заполнить `answer.json` по шаблону и исправить только runtime `candidate.py`.
   Использовать Python/bash для собственных вычислений разрешено.
6. Сдать **ровно один раз**:

   ```bash
   python src/admission.py check --session-log logs/session-YYYY-MM-DD-NNN.md
   ```

7. Checker сам записывает в лог ровно один машиночитаемый marker результата.

Удаление runtime, повторный `issue`, повторный `check`, изменение checker/policy, подмена HEAD или
ручное написание marker запрещены и означают непройденный допуск.

## Состав challenge v1

1. **Constraint fidelity:** классифицировать действия как разрешённые/запрещённые по этой policy.
2. **Constraint solving:** найти единственный порядок задач по случайным ограничениям и checksum.
3. **Code repair:** исправить runtime-функцию по спецификации; checker запускает фиксированные и
   случайные скрытые случаи в отдельном процессе с timeout.

Все три категории имеют одинаковый вес. Порог допуска — **3/3**. Частичный балл не даёт права
на содержательную работу.

## Реакция на результат

### PASS

- В логе появляется marker `CAPABILITY_ADMISSION: PASS` без сведений об идентичности.
- Можно продолжить ритуал пробуждения: общая верификация, retrieval, гипотезы и работа.
- PASS не отменяет тесты результата и ручной review создателя.

### FAIL или ошибка протокола

- В логе появляется marker `CAPABILITY_ADMISSION: FAIL` либо отсутствует допустимый PASS.
- Немедленно прекратить содержательную работу.
- Не менять память, код и документацию; не делать commit и push.
- Ответить создателю одной фразой:

  `Допуск к содержательной работе не пройден; сессия остановлена.`

Нельзя объяснять провал догадкой об идентичности модели.

## Защита от ложной уверенности

- Gate проверяет минимальную готовность, а не качество всей будущей сессии.
- Случайность мешает заучиванию конкретного ответа, но не устраняет benchmark overfitting.
- Форматные ошибки считаются реальными ошибками instruction-following; шаблон снижает их случайность.
- Сложность и порог нельзя смягчать внутри провалившейся попытки.
- После серии реальных сессий результаты нужно сравнить с ручными merge/reject-решениями и
  измерить false accept/false reject. До такой калибровки gate имеет статус экспериментального.

## Критерий остановки

Процедура закончена, когда checker записал единственный PASS/FAIL-marker. PASS открывает следующую
стадию пробуждения; любой другой исход закрывает сессию.
