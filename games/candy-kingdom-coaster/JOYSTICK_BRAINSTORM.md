# Телефон-джойстик для VR-поездки — мини-брейншторм и стенд задержки

> Статус: **контракт стенда утверждён, стенд реализован (2026-10-15)**.
> Полный режим в игру не встраивается, пока стенд не замерит задержку
> на устройствах пользователя.

## Исходный запрос (дословно, 2026-10-15)

«…дополнительное управление с другого телефона… который будет подключаться
к заезду в режиме джойстика. Типа два телефона конектятся к одной "комнате".
Один телефон становится экраном, а другой джойстиком с только двумя
кнопками. Подключаются по Гугл фаербазе. Проблема в том не будет ли слишком
большая задержка реакции. С учётом того что оба устройства работают через
VPN в интернете. И не съест ли трафик весь мой бесплатный лимит на Гугл
фаербазе»

Решение пользователя после разбора: «Сделай и то и другое» (мини-брейншторм
+ прототип-стенд замера задержки).

## Аналитические выводы (до брейншторма)

- Задержка через Firebase Realtime Database при обоих телефонах за VPN:
  типично ~150–300 мс нажатие→поворот, всплески до 600–900 мс. Для этой
  игры (машинка едет сама, проиграть нельзя) терпимо; критерий прототипа —
  медиана ≤ 300 мс.
- Трафик: только события нажатия/отпускания в Realtime Database — сотни
  килобайт на заезд при бесплатном лимите 10 ГБ/мес. Firestore как
  транспорт запрещён: 10 событий/сек = 36 000 записей/час при лимите
  20 000 записей/день.
- WebRTC (план Б): прямое соединение телефонов, Firebase только знакомит
  (сигналинг). Задержка ~30–120 мс, но сложнее NAT/VPN-проход и нужен TURN.

## Этап 1 — Продукт (ответы пользователя, 2026-10-15)

| Вопрос | Ответ | ID |
|---|---|---|
| Кто с джойстиком | **Один игрок с двумя телефонами**: свой второй/старый телефон — пульт, экранный телефон — в очках | `solo_two_phones` |
| Подключение | **Только 6-значный код** комнаты (без QR и ссылок) | `code_only` |
| Цель стенда | **Замерить на своих VPN и решить по цифрам** (вариант 1 + просьба объяснить WebRTC — объяснено в чате) | `measure_then_decide` |

Следствие из `solo_two_phones`: подключение и интерфейс можно делать
максимально простыми и «для себя» — без детской пары ролей, без приглашений
в мессенджеры; главный вопрос стенда — задержка именно на устройствах и
VPN пользователя.

## Этап 2 — Контракт стенда (утверждён пользователем, 2026-10-15)

`approve_mvp`: отдельная страница-стенд `joystick-stand/` (в игру ничего не
встраиваем). Экран создаёт комнату по 6-значному коду, Джойстик вводит код.
Джойстик пишет в Realtime Database только нажатия/отпускания; Экран
показывает состояние руля, задержку последнего события, медиану и p95 по
пинг-понгу, счётчики сообщений и трафика, вердикт «≤ 300 мс — играбельно на
Firebase / хуже — нужен WebRTC». Демо-режим в двух вкладках без Firebase.
Не делаем: интеграцию в игру, QR, WebRTC-транспорт, аккаунты. Правила базы
стенда — тестовые «по коду», с предупреждением.

# СТЕНД РЕАЛИЗОВАН (2026-10-15)

`joystick-stand/index.html` — одна страница, две роли (Экран / Джойстик),
комната по 6-значному коду; `joystick-stand/README.md` — инструкция по
бесплатному Firebase-проекту за 10 минут.

- Транспорт Firebase (Realtime Database, europe-west1 у пользователя):
  только события нажатия/отпускания, пинг-понг каждые 2 с, статистика
  медиана/p95 и счётчики трафика на обоих ролях, вердикт по критерию
  «медиана ≤ 300 мс». Задержка события считается по серверному времени
  (`serverTimestamp` + `.info/serverTimeOffset`) — часы телефонов не важны.
- Демо-режим без Firebase (BroadcastChannel, две вкладки): проверка
  интерфейса и логики; задержка ~0, сетевую картину не показывает.
- Проверка `tests/tools/joystickqa.mjs` — **7/7** в демо-режиме (комната,
  руль до экрана, реальное касание кнопки, пинг-статистика и вердикт,
  счётчики, без ошибок). Скриншот: `tests/evidence/joystick-stand.png`.
- Не проверено в песочнице: настоящий Firebase-путь (нужен проект
  пользователя) — это и есть следующий шаг замера на двух телефонах с VPN.

# ЗАМЕРЫ ПОЛЬЗОВАТЕЛЯ (2026-10-15, два телефона, оба через VPN)

| Метрика | Значение |
|---|---|
| Пинг-понг RTT, медиана | 295 мс |
| В одну сторону ≈ RTT/2, медиана | **148 мс** |
| В одну сторону, p95 | 225 мс |
| Замеров пинга | 30 |
| Сообщений отправлено / получено | 229 / 160 |
| Задержка события (на джойстике) | «—» (эта метрика живёт на стороне Экрана, не на Джойстике) |

**Вердикт по критерию контракта (медиана ≤ 300 мс): ПРОЙДЕН с двукратным
запасом.** Даже p95 (225 мс) ниже порога. Решение: транспорт режима —
Firebase Realtime Database, WebRTC откладывается как ненужный при таких
цифрах (вернуться к нему, только если на других сетях медиана уйдёт за
300 мс). Трафик: ~389 сообщений за сессию замера — килобайты при лимите
10 ГБ/мес, вопрос закрыт.
