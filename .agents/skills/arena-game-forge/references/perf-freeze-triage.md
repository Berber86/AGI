# Фризы мобильного 3D: пофреймовая диагностика, шейдерные пермутации, прогрев

Полевой опыт кампании «тест фризов» (games/pelagic-eye, Android Chrome 155, Mali-G57 MC2
и Adreno 610). Главный урок: самые «нереальные» тормоза мобильного 3D — это шейдеры, и
они отлично маскируются под «медленный рендер», «композитор» и «слабое железо».

## 1. Шейдерные пермутации — главный источник «нереальных» тормозов

Один и тот же `material` даёт РАЗНЫЕ GLSL-программы в разных условиях рендера:

1. **Рендер-таргет.** Кадр в канвас (прямой рендер, VR-стерео по глазам) и кадр в
   offscreen-таргет composer'а (HalfFloat + ACES) компилируются с разными
   tonemapping/output-пермутациями ключа программы. Материалы, «прогретые» в одном
   таргете, ничего не говорят о другом.
2. **Тени.** `light.castShadow = false` меняет `numShadows` в ключе → ещё один набор
   программ на каждый материал. VR-губернатор, гасящий тени на тяжёлом tier'е, сам
   устраивает локальный шторм пересборки (~30 программ).
3. **Ночь/LOD/классы/качество.** Переключаемые по `visible`/defines варианты материалов
   (ночные наборы, «дальние» LOD, классы существ) добавляют свои программы.

Реальный кейс: вход в VR собрал +36 программ прямо в первом стерео-кадре
(отчёт: «рендер 36558мс при GPU 0.5мс»), автосрез губернатора добавил ещё +29 посреди
игры. Итог — 2 кадра за 37 секунд на телефоне, который после лечения выдал 40 FPS.

## 2. `linkProgram` бесплатен, а компиляция — до ПЕРВОЙ отрисовки

С `KHR_parallel_shader_compile` (ANGLE на Android) вызов `linkProgram` возвращается
мгновенно — в отчётах «линковок 136, суммарно 1мс» — а настоящую компиляцию драйвер
держит **до первого draw с этой программой**. Поэтому:

1. Счётчик `linkProgram` ловит пермутационный шторм, но НЕ показывает его стоимость.
   «Линковки дармовые» ≠ «шейдеры дешёвые».
2. Прогрев обязан состоять из двух половин:
   **сборка** (`renderer.compile` — линки) и **прожиг** (реальная отрисовка каждой
   программы — компиляция прогорает в лобби, а не в первом VR-кадре).
3. Прожиг без порчи кадра: нарисовать меш реальным `renderer.render` в угол канваса
   2×2 (`setViewport/setScissor(0,0,2,2)`, `setScissorTest(true)`, `autoClear=false`),
   затем восстановить viewport/scissor/autoClear. Не в offscreen-таргет — это другая
   пермутация! И не полным кадром — иначе фриз просто переедет в лобби.

## 3. `renderer.compile(obj)` от под-объекта компилирует «вслепую»

`compile(mesh)` строит состояние света от переданного корня: у меша нет светильников →
`numLights = 0` → программа выходит «слепой», а реальный рендер со светом соберёт свою.
Симптом: прогрев вроде бы прошёл, а при входе в VR всё равно шторм.

Правило: **компилировать от ПОЛНОЙ сцены**, временно маскируя видимость:
текущий меш видим, остальные меши скрыты, светильники и группы видимы, скрытые
ночные группы — принудительно включены. Очередь — по мешам (не по группам! группа с
60 материалами = 60-секундный фриз в одном шаге), бюджет ~55мс на кадр: дорогая
линковка выходит за бюджет, дешёвые догоняются пачками. После смены материалов
(`needsUpdate`, бюджета качества) — новая очередь прогрева.

## 4. Тест фризов 15с: пофреймовый пробник

Счётчики каждого кадра: `wall`, `update` (по подсистемам: пути/школы/частицы), `render`
(глаз0/глаз1/composer), `gpuWait` (`gl.finish` — ТОЛЬКО во время теста), «вне кадра»,
длинные JS-задачи, LoAF (`user-callback`/`event-listener` + style/paint), GC-паузы,
UI-цикл панели, тики камеры, события (resize/fullscreen/vr/stall/gov/shader:link).

Как читать отчёт:

1. **GPU-ожидание (`gl.finish`) ~0 при огромном render** → дело НЕ в fill rate; GPU
   свободен, время съедает CPU/драйвер/компиляция.
2. **«Вне кадра» большая** → композитор/презентация, инкрементальный GC, система.
3. **Длинные JS-задачи:** топ `user-callback:index.html` — сам игровой цикл;
   `event-listener:index.html` — обработчики UI/событий.
4. **«камера в полёте»** — фриз совпал с обработкой тика камеры (тег `camBusy`).
5. **«Шейдеры: линковок N»** — счётчик пермутаций, а не времени (см. п. 2).
6. Классификация фриза — по наибольшей компоненте (≥30%); порог фриза 50–150мс;
   первый кадр прижимается к границе окна (иначе дозамеренный разрыв «утекает» в
   статистику); сумма фризов ≤ 120% окна — иначе замер нечестный.

A/B-приёмы: чекбокс «без стекла» снимает `backdrop-filter`-оверлеи живым style-тегом
(стоимость композитора Android); **обход composer'а отклонён** — ACES применяется до
смешения прозрачностей, A/B-скриншоты дают 40% расхождения при шуме 1–2%. Оптимизация
GPU — через overdraw/разрешение, не через цветовой пайплайн.

## 5. Фингерпринты (не путать между собой)

1. **Шторм пермутаций:** первые кадры после входа в VR/смены профиля по 2–30с, GPU-ожидание
   ~0, «длинные задачи» = сам рендер. Лечение — пп. 1–3.
2. **Давление памяти/тепло:** JS-heap вырос в разы против базового замера + ВСЁ медленнее
   разом (update сцены, анализ, bitmap) + огромная «вне кадра» при «GC-паузах» 0 — это
   инкрементальная разметка GC или троттлинг системы, а не баг конкретной подсистемы.
   Сравнивать всегда с базовым замером ТОГО ЖЕ устройства (как выглядит «норма»).
3. **Разброс устройств:** Mali-G57 MC2 (ANGLE/ARM) и Adreno 610 (Qualcomm) на одном и том
   же сценарии отличались в разы: линковка ~0.8с против <0.01мс на вызов, CPU-сабмит
   рендера в ~12 раз. «Слабое железо» — последняя гипотеза, после замера.

## 6. QA-контракты (пример pelagic-eye)

1. `qa/shaderwarmup.mjs` — счётчик `linkProgram`/`compileShader` на прототипе WebGL
   (`addInitScript`); ассерт: после прогрева look-around, вход в VR и VR-игра дают
   ≤2 новых линковок (было +36/+29); снимок числа программ start→end.
2. `qa/reeffreeze.mjs` — искусственный busy-loop 400мс: пробник обязан поймать фриз и
   классифицировать его как «длинная JS-задача», сумма фризов ≤ 120% окна.
3. `qa/static-serve.mjs` — самодостаточный статик-сервер внутри репо (не зависит от
   `/home/user/tools`, который сбрасывается).
4. Хуки страницы: `window.__REEF__` (мир), `window.__PROBE__` (пробник),
   `__PE_WARMUP_DONE__` (прогрев завершён). Имена фиксированные — не изобретать заново.

## 7. Ловушки замеров

1. `npm run build` собрал ≠ тест гоняет новое: публикация демо-страницы может быть
   отдельным шагом (`export:static` копирует бандл в `play/index.html`). Сверять, что
   тестируемый бандл реально пересобран, иначе часами «чинишь» старый код.
2. События пробника: `ring` (последние 200 — всегда) против `events` (только во время
   замера). Пост-мортем по «События замера» может не показать важное — читать `ring`.
3. Просите отчёт целиком: шапка устройства + строки «Кадры», «GPU-ожидание», «Шейдеры»,
   «Виновники», «Худшие кадры». Виновник определяется по компонентам, а не по ощущениям.
