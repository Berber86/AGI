# Сбросы окружения/репозитория и восстановление

Песочница Arena периодически **сбрасывается до снапшота** между ходами. Этот документ описывает, что именно теряется, как это выглядит и как восстанавливаться с минимальной потерей работы.

## Что переживает сброс, а что нет

| Переживает | Теряется |
|---|---|
| git-чекаут рабочего репозитория (например `/home/user/AGI`) — **отслеживаемые файлы и рабочее дерево** | файлы **вне** чекаута: `/home/user/tools`, любые артефакты за пределами репо |
| удалённый GitHub (всё, что запушено) | `node_modules` — **в том числе ВНУТРИ чекаута** (`npm ci` по package-lock), кэш npm, содержимое `/tmp` (бинарники браузера, скомпилированные шрифты) |
| содержимое рабочего дерева на момент снапшота | **запущенные серверы и фоновые процессы** |
| | **локальная git-история**: незапушенные коммиты исчезают; ветка может «откатиться» к старому коммиту, а рабочее дерево остаться новым |

## Симптомы сбоя

- `ls /home/user/tools` → `No such file or directory` (хотя вы его создавали);
- `curl http://127.0.0.1:<порт>/…` → `000` (сервер мёртв);
- `git log --oneline -5` **не показывает** коммиты, которые вы делали (HEAD указывает на старый commit);
- `git push` отклонён: `non-fast-forward` / «fetch first»;
- в `git status` все файлы игры вдруг «новые» (`A`), хотя вы их давно коммитили.
- unit-тесты падают с `Cannot find package 'three'` (или другой зависимости) — снесли `node_modules` внутри чекаута; лекарство: `npm ci --ignore-scripts` в каталоге игры.

## Порядок восстановления (проверенный)

### 1. Инструменты и браузер

```bash
mkdir -p /home/user/tools && cd /home/user/tools
npm init -y && npm install puppeteer-core sharp @sparticuz/chromium
node setup-runtime.mjs      # распаковка /tmp/chromium + библиотек — см. headless-browser-setup.md
```

`setup-runtime.mjs` держите воспроизводимым (полный текст — в `headless-browser-setup.md`), либо складывайте в сам репозиторий, чтобы не переписывать по памяти.

### 2. Серверы

```bash
cd <repo-root> && nohup python3 -m http.server 8899 &          # тестовый
# живое превью пользователя — через start_process на 0.0.0.0
```

### 3. Git: сверить локальную историю с удалённой

```bash
git fetch origin <ветка-сессии>
git log --oneline -5
git log --oneline origin/<ветка-сессии> -5
```

Три случая:

**а) Локальная ветка отстала, рабочее дерево тоже старое** — просто `git pull --rebase` (или reset --hard на origin, если правок нет) и продолжайте.

**б) Рабочее дерево НОВОЕ (ваши правки на месте), а история откатилась** — типичный случай снапшота. НЕ делайте `git pull` (получите конфликты «файл уже существует» по всей игре) и НЕ делайте `git reset --hard` (уничтожите новые правки). Правильный приём — **reset на удалённую историю и новый коммит поверх**:

```bash
git reset --mixed origin/<ветка-сессии>   # HEAD+индекс прыгают на удалённый tip; рабочее дерево сохраняется
git status --short                        # теперь видна РОВНО дельта «новое поверх origin»
git add <только свой scope> && git commit  # аккуратный коммит только своей дельты
git push origin <ветка-сессии>            # должен пройти fast-forward'ом
```

`--mixed` предпочтительнее `--soft`: при `--soft` индекс остаётся от старой базы, и в один коммит сваливается весь промежуточный диф (сотни строк «уже есть в origin»). `--mixed` пересобирает индекс по origin — коммит получается ровной дельтой. Если `git status` показывает лишнее (например, всплыли файлы из старой эпохи) — разберите их до `git add`, не тащите мусор.

Никогда не `git add -A` вслепую: в дельте после снапшота почти всегда сидят перегенерированные tracked evidence (скриншоты/отчёты браузерных QA) и дубли файлов чужих игр. Лишнее восстанавливайте `git restore <paths>`, стейджьте только свой scope и проверяйте `git diff --cached --stat` до коммита. Реальный случай: рабочее дерево из 59 записей при нужных 21 файле одной игры.

**в) Локальная история разошлась с удалённой (обе впереди)** — сначала разберитесь, чьи коммиты ценнее (обычно удалённые — это уже опубликованная работа). Затем либо `git rebase origin/<ветка>` по конфликтам, либо вариант (б), если содержимое вашего дерева включает всё нужное.

### 4. Проверка

- `git status` — чисто;
- `git log --oneline -3` — ваш коммит стоит **поверх** `origin/…`;
- `git push` — прошёл без `non-fast-forward`;
- прогоните автотесты/скриншоты заново (среда-то новая).

## Профилактика

1. **Пушите после каждого пользовательски-видимого этапа** — удалённая ветка сессии единственный долговечный склад. Незапушенная работа при сбросе теряется из истории (хотя и может уцелеть в рабочем дереве).
2. Держите воспроизводимыми: скрипт распаковки браузера, команды установки тулзов, команды запуска серверов — в документах скилла или в репозитории.
3. Не складывайте рабочие артефакты вне чекаута репозитория. Скриншоты-evidence — в `tests/evidence/` (или аналог) **внутри** репо.
4. В конце каждого хода фиксируйте в памяти сессии: последние хэши коммитов, состояние серверов, где лежат тулзы — так восстановление превращается в 5 минут по чек-листу.
