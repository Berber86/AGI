# Дешёвые сенсоры и приёмы для VR на телефоне: каталог

Этот документ — не «список гаджетов», а карта **дефицита возможностей**. Он
для случая: линзовые очки из картона, телефон-экран, второй телефон-пульт,
гироскоп/акселерометр и камера с цветной меткой уже есть. Вопрос — что ещё
можно позволить за копейки.

Читать вместе с [immersive-vr-remote-input.md](immersive-vr-remote-input.md):
там контракт, знаки, fusion-предохранители и замеры. Здесь — что добавлять
**после** того, как §4а работает.

Метки статуса те же, что во всём skill: `device-tested` — проверено на живом
телефоне; `synthetic` — проверено математикой/headless-тестом; `idea` — не
проверено вообще, оценивайте скептически.

---

## 0. Сначала дефицит, потом покупка

У текущего стека шесть настоящих дыр. Каждая покупка без привязки к дыре —
это игрушка на полке.

| Дефицит | Как выглядит в игре | Самое дешёвое закрытие | Цена |
|---|---|---|---|
| Нет **поступательного** движения (только 3DoF) | нельзя наклониться, шагнуть, подойти к объекту; мир «прибит» к голове | fiducial-метка → homography → PnP (§1.1) или камера снаружи (§3.1) | печать / 0–20 € |
| **Дрейф yaw** | через 2–3 минуты «север» уехал, комната повернулась | компас как медленный якорь (§1.2) или тег на стене | 0 € |
| Метка = **цветное пятно** без ID и углов | ложные срабатывания на игрушках, нет ориентации, нет масштаба | AprilTag/ArUco (§1.1) | ~0,5 € |
| Пульт = **2 кнопки на 33 Гц** | нельзя навести, повернуть, потянуть | 3DoF-указка + транспорт без Firebase (§3.3, §5) | 0 € |
| Неизвестны **FOV и дисторсия** линз | неверный масштаб мира, «плоское» стерео, укачивание | калибровка по метке и линейке (§1.7) | 0 € |
| Нет **измерения** задержки/джиттера позы | спор о «тормозит» без цифр | съёмка экрана в slow-mo (§6) | 0 € |

Правило: если идея не двигает одну из строк этой таблицы — она в раздел
«поиграться», а не в продукт.

## 1. Уровень 0 — бесплатно, из того, что уже в руках

### 1.1 Печатная fiducial-метка вместо цветного пятна

Самая большая отдача за 50 копеек. Цветное пятно даёт `{found, centroid,
count}`. Тег даёт **ID + 4 субпиксельных угла**, а из четырёх углов
выводится полная поза в 6DoF.

Конвейер (тот же Worker, что уже есть в `camtrack`):

```text
кадр → grayscale → адаптивный порог (интегральное изображение)
     → контуры → аппроксимация до 4 углов → гомография
     → декод битовой матрицы (ID, поворот, чётность)
     → уточнение углов (пересечение линий, субпиксель)
     → pose (R, t) в метрах
```

Почему это принципиально другой класс надёжности, чем HSV:

- **ID** отсекает ложные квадраты; цвет — нет;
- **биты** дают поворот и защиту от ошибки (у AprilTag/Hamming-код);
- **известный физический размер** даёт метры без калибровки сцены;
- **4 угла** дают ориентацию плоскости, а не только «где-то там».

Бюджет разрешения — считается, а не угадывается. Для pinhole
`f_px = (W/2) / tan(HFOV/2)`, сторона тега в кадре `p ≈ f_px · s / d`.
Нужно ≥ 5 px на модуль (у tag36h11 матрица 8×8 модулей → ≥ 40 px на сторону).

| Кадр | HFOV | f_px | A4 (0,20 м) читается до | 10 см до |
|---|---|---|---|---|
| 320 px | 70° | 229 | ~1,1 м | ~0,55 м |
| 640 px | 70° | 457 | ~2,3 м | ~1,15 м |
| 960 px | 70° | 686 | ~3,4 м | ~1,7 м |

Отсюда **двухъярусная схема**, которая не убивает FPS:

```text
каждый кадр (160–224 px, ~15–20 Гц): HSV-блоб → «метка в кадре / нет»
6–10 Гц (480–640 px, отдельный кадр): тег → точная поза
```

Блоб отвечает за живость и за потерю, тег — за метры и углы. Это то же
правило адаптивных ярусов, что уже принято для `camtrack`, только теперь
дешёвый ярус решает другую задачу.

**Поза из гомографии без OpenCV.** Для плоскости тега `H = K·[r1 r2 t]`,
`K = [[f,0,cx],[0,f,cy],[0,0,1]]`, размер тега нормируется в 1:

```js
// H — гомография unit-square → изображение, h33 = 1
const Kinv = (h) => [                       // столбцы K⁻¹·h
  [(h[0] - cx * h[6]) / f, (h[1] - cx * h[7]) / f, (h[2] - cx * h[8]) / f],
  [(h[3] - cy * h[6]) / f, (h[4] - cy * h[7]) / f, (h[5] - cy * h[8]) / f],
  [h[6], h[7], h[8]],
];
// h — массив из 9 чисел по строкам; a1..a3 — столбцы после K⁻¹
const lam = 2 / (Math.hypot(...a1) + Math.hypot(...a2));   // усреднение шума
const r1 = a1.map(v => v * lam), r2 = a2.map(v => v * lam);
const r3 = cross(r1, r2);
// t = lam · a3 · s, где s — физическая сторона тега в метрах
```

Дальше `r3` и ортонормировка `R` (Грам–Шмидт или полярное разложение).
Матан проверяется юнит-тестами на синтетической позе: известные `R, t` →
проекция углов → гомография → обратно `R, t` с точностью ≤ 1 мм / 0,5°.

Подводные камни, которые съедают вечер:

- **Две ветви решения** для компланарных точек (классическая ambiguity).
  Разрешается асимметрией кода и историей: ветвь, которая прыгает между
  кадрами, — неверная.
- **Дрожание** на низком разрешении — это шум **позы**, а не углов.
  Сглаживайте `t` и `R` раздельно и с разными постоянными; сглаженную позу
  нельзя подавать обратно как «измерение» (§4а).
- **Печать**: ламинация убирает блики; на глянцевой бумаге метка «мокнет»
  от любого окна. Матовая — обязательно.
- **Наклон**: тег под углом > 60° к камере декодируется плохо. В комнате
  нужны 2–3 тега, а не один.

### 1.2 Компас: абсолютный yaw как медленный якорь

Гироскоп — единственный источник, который не врёт **в коротком** окне и
всегда врёт **в длинном**. Магнитометр — наоборот. Портативный путь в
браузере — `deviceorientationabsolute` (не сырой `Magnetometer`: он за
флагом и не на всех Android).

Использовать строго как ещё один якорь по правилам §4а: confirmation,
grace, rate limit. Дополнительно:

- отбрасывать поправку, если модуль поля ушёл от калиброванного;
- отбрасывать, если скачок heading больше порога за один интервал;
- не включать автоматически: в комнате с колонками, ноутбуком и
  холодильником компас врёт предсказуемо плохо, и «умное» включение
  выглядит как поломка управления.

В метро-игре это буквально механика: «компас показывает не туда» — сюжет.

### 1.3 Микрофон

Самый недооценённый сенсор, потому что он уже прижат ко рту в очках.

- **Дунуть**: широкополосная энергия 200–2000 Гц, нет основного тона,
  устойчиво > 150 мс. Речь отличается гармониками — проверяйте
  спектральную «плоскость», а не громкость.
- **Крик/уровень**: RMS относительно шумового пола, откалиброванного в
  меню. Без калибровки «громко» зависит от чехла и комнаты.
- **Ритм**: onset-детектор по производной энергии. Годится для «хлопни»,
  «топни», «сыграй мелодию».
- **Свист**: узкий пик 1–3 кГц, отличный дискретный сигнал.

Честные ограничения: шум вентилятора, музыка из колонок, эхо комнаты.
Порог всегда калибруется, а не хардкодится.

### 1.4 Экран второго телефона — это управляемый источник света

Второй телефон в руке — не только пульт.

- **Подсветка** для ретрорефлективных меток (§2.1) — фонарик или белый
  прямоугольник на весь экран.
- **Активная метка с точно известной геометрией**: размер экрана в мм
  известен, яркость и цвет известны — идеальная мишень для PnP, если
  напечатанной бумаги под рукой нет. Плюс метка может **мигать кодом**
  (частота/последовательность), чтобы различать два телефона.
- **Экран как «портал»**: если транслировать камеру второго телефона в
  очки (§5), получается окно в реальный мир — дешёвый mixed reality без
  ARCore. Для детективной игры «камера в другой комнате» это готовая
  механика.

Осторожно: авто-яркость, ШИМ-мерцание, разница цветов между матрицами,
роллинг-шаттер. Для сравнения яркостей между устройствами экран не
годится, для геометрии и «есть/нет» — годится.

### 1.5 Свет и экспозиция как датчик

Средняя яркость уменьшенного кадра, который и так уже считается в Worker:

- выключили свет в комнате → событие в игре (и проверка, что камера жива);
- накрыли камеру рукой → «очки сняты» → пауза;
- вспышка в комнате → синхронизация (см. §6).

Это бесплатный датчик присутствия, которого нет ни в одном API.

### 1.6 Фронтальная камера смотрит в лицо

В картонных очках фронталка находится между линзами, у носа. С маленьким
зеркальцем (1 €, лучше first-surface) можно увидеть глаз и поймать моргание.
Моргание — отличный дискретный input: «подтвердить», «переключить».

Статус: `idea`. Проблемы реальные — фокус на 5–10 см, нос в кадре, темно.
Проверять на своей модели очков до того, как строить на этом механику.
Полноценный eye-tracking так не сделать: только «моргнул/не моргнул» и
грубое «смотрит влево/вправо».

### 1.7 Бесплатное, что ощущается как новое железо

Порядок — по отдаче на слабом телефоне.

1. **Fixed foveated rendering** (низкое разрешение по краям, полное в
   центре). На Mali-G57 экономия fill rate больше, чем даст любая покупка.
2. **Late latching / reprojection**: рендер по прошлой позе, на подаче —
   домножение на дельту гироскопа. Режет воспринимаемую задержку на
   20–40 мс.
3. **Предсказание позы** по угловой скорости с ограничением (не
   предсказывать рывки).
4. **Дисторсия и хроматическая коррекция** — предыскажение кадра под линзу.
   Без неё «VR» остаётся «двумя картинками». Модель Brown–Conrady с двумя
   коэффициентами, подобранными глазами по тестовой сетке, уже даёт эффект.
5. **Замер FOV линейкой и меткой**: тег размера `s` на расстоянии `d`
   занимает `p` пикселей → `f = p·d/s`, `HFOV = 2·atan(W/(2f))`. Спековые
   FOV в характеристиках телефона относятся к фото, а не к видеопотоку —
   мерить надо свой.
6. **Tunnel vision** при движении (поле зрения сужается) — сильный
   антитошнотный приём, стоит ноль.

## 2. Уровень 1 — печать, скотч, коврик (≤ 10 €)

### 2.1 Ретрорефлективная лента + фонарик

Полоска 3M-подобной ленты (3–8 €) на стене или на предмете возвращает свет
источника обратно в камеру. В отличие от цветной бумаги, которая при смене
освещения меняет HSV, ретрорефлектор меняет только яркость — и остаётся
**на порядок ярче** окружения.

- Работает в полутёмной комнате, устойчив к цветному окружению.
- «Фонарь освещает метку» → механика: у игрока реальный фонарь (второй
  телефон), а мир реагирует только на подсвеченное.
- Яркий blob проще и быстрее HSV (одна яркость + площадь), значит дешёвый
  ярус §1.1 становится ещё дешевле.

Не проверено на телефоне: `idea`. Проверять при выключенном/включённом
свете и с разным углом.

### 2.2 Коврик как граница и как масштаб

Самый дешёвый chaperone — не софт, а ноги. Коврик/мат с выраженным краем:
игрок чувствует границу площадки телом, без единого пикселя UI. Это
согласуется с правилом «ноль HUD».

Бонус: если положить на пол **рисунок с масштабом** (шахматка, полосы,
большой тег), камера, направленная вниз, получает и масштаб, и абсолютную
привязку, и текстуру для optical flow. Коврик с геометрическим узором на полу
превращает «камера смотрит в пол» в полноценный трекер: масштаб известен
заранее, а углы и позиция считаются по той же гомографии, что и для тега
(§1.1), только мишенью служит фрагмент узора.

## 3. Уровень 2 — камера снаружи (0–25 €)

### 3.1 Outside-in: старый телефон на штативе следит за очками

Главный способ получить **настоящее 6DoF головы**, не покупая VR-железо.

```text
[телефон на штативе, неподвижен] --WebRTC/WS--> [телефон в очках]
        камера + тег на очках → pose (R,t)           гироскоп 60 Гц
                                                      ↓
                                            fusion: гироскоп ведёт,
                                            поза правит дрейф и даёт t
```

- На очки клеится тег (или два тега на согнутом картоне под 90°, чтобы
  один был виден всегда).
- 15–30 Гц видения достаточно: это **корректор**, а не источник взгляда.
  Для «наклониться к объекту» нужна именно позиция, а не поток.
- Требуется калибровка интринсиков этой камеры (шахматка, 5 минут) — иначе
  `t` будет врать на 10–20 %.
- Задержка в тракте видения 60–120 мс; fusion-предохранители §4а
  обязательны, иначе один плохой кадр телепортирует игрока.
- Обязательное условие: **неподвижная камера**. Любой сдвиг штатива =
  обнуление мира.

Почему это интересно именно вам: код почти весь уже написан (детектор,
Worker, fusion), добавляется только PnP. Один вечер — и появляется
«наклониться», «шагнуть», «обойти столб».

Дешёвая версия: ноутбук с веб-камерой как наблюдатель и WebSocket на
localhost — тогда вся математика уезжает с телефона.

### 3.2 Маркерный «контроллер» из картона

Тот же стек, другая мишень: картонка с тегом = рука. Один тег даёт
позицию + 2 оси вращения, два тега на «пистолете» — полную ориентацию.
В отличие от 3DoF-указки (§3.3), это настоящий 6DoF-контроллер, и он
работает **без сети** — вся геометрия в кадре.

Ограничение: рука должна быть в поле зрения камеры очков (или внешней
камеры) и не перекрыта.

### 3.3 Телефон-джойстик как 3DoF-указка

`DeviceOrientation` второго телефона → абсолютная (с компасом) или
относительная ориентация. Годится для фонарика, меча, «волшебной палочки»,
наведения на виртуальный экран.

- Только вращение: поступательного движения нет, и интегрировать
  акселерометр в позицию — известный тупик (метры дрейфа за секунды).
- Знаки — строго по §2, одна семантика на проект. Второй набор «потому что
  тут телефон повёрнут иначе» — источник багов на месяц.
- 33 Гц через Firebase превращает указку в слайд-шоу (см. §5).

## 4. Уровень 3 — ESP32/BLE (10–30 €)

Когда телефона не хватает по форм-фактору: на ногу, на руку, на стену.

| Что | Компоненты | Что даёт | Честные пределы |
|---|---|---|---|
| Foot pod | ESP32-C3 + MPU6050 (8–12 €) | walking-in-place, каденс → скорость, счёт шагов | 20–50 мс BLE, калибровка под походку, 2–4 ч на батарейке |
| ToF-дальномер | VL53L1X (8–12 €) | 4 м, 50 Гц, настоящая дистанция: chaperone, сонар, «горячо/холодно» | конус ~27°, не любит чёрное и стекло |
| Ультразвук | HC-SR04 (2 €) + ESP32 | то же, дешевле, шире конус | 20 Гц, 15°, шумит от эха, нужен микроконтроллер |
| Сжатие/вес | FSR (3 €) + АЦП | «сжать», «наступить», «натянуть» | дрейф, нужна калибровка нуля |
| Магнитный проп | неодим (3 €) + QMC5883L (3 €) | позиция пропа в радиусе 5–20 см | диполь падает как 1/r³, металл в комнате врёт |
| Кнопка/педаль | любой BLE-HID (5–20 €) | мгновенный input без сети | нет аналоговых осей (кроме геймпада) |

Практика, которая экономит неделю:

- **BLE — не Wi-Fi.** 20–50 мс и 30–100 Гц реальны; 200 Гц — нет.
- **Web Bluetooth только на Android Chrome.** iOS — не рассматривать.
- **Батарейка и сопряжение** — это операционные расходы, которые съедают
  «поиграть пять минут». Прошивка должна переподключаться сама.
- **Датчик на ноге** надо крепить так, чтобы он не отваливался при
  прыжке — иначе игра про шаги превращается в игру про провод.

Магнитный проп — самая недооценённая идея: старый принцип Polhemus в
миниатюре. Магнит N52 10×3 мм даёт ~26 мкТл на 10 см — это уровень
магнитного поля Земли, то есть уверенно детектируется. Но **сырой
магнитометр в браузере недоступен** (за флагом), поэтому это проект для
ESP32, а не для `DeviceOrientation`.

## 5. Транспорт: один Firebase на всё не тянет

Уже измерено: Firebase RTDB, два телефона за VPN — 148 мс в одну сторону,
p95 225 мс, и это отлично для кнопок. Но каждый новый сенсор меняет
требования.

| Поток | Частота | Firebase RTDB | Вывод |
|---|---|---|---|
| 2 кнопки руля | ~33 Гц событиями | 148 мс медиана | годится (замерено) |
| 3DoF-указка | 60 Гц | нет | нужен WebRTC/WS |
| Поза от внешней камеры | 15–30 Гц | нет | нужен WebRTC/WS |
| Видео с второго телефона | 30 Гц кадры | нет | только WebRTC |

Лестница транспорта:

```text
WebRTC datachannel (LAN)  ~5–30 мс   → поток позы, указка, события
WebSocket на локальный сервер ~5–20 мс → то же, проще отлаживать
Firebase RTDB             ~150 мс    → знакомство, комнаты, редкие команды
```

Правило: **Firebase остаётся сигналингом и «пультом», а поток идёт
напрямую**. Стенд `joystick-stand/` уже умеет мерить; для потоковых
режимов нужен второй стенд — с sequence-номерами на 60 Гц и статистикой
джиттера (p50/p95/p99), а не только медианой.

## 6. Измерения, которые полезнее покупок

Всё ниже делается тем, что уже есть на столе.

1. **Motion-to-photon, slow-mo.** Второй телефон снимает экран в очках на
   120–240 fps. Резко поверните голову (или мигните светодиодом) и
   посчитайте кадры от физического события до смены картинки. Типичные
   60–120 мс для картона — и вы увидите, сколько из них добавляет ваш
   рендер, а сколько композитор.
2. **Джиттер позы.** Тег неподвижен 10 с. Считайте std и p95 по `t` и по
   углам — отдельно. Это честный ответ «дрожит или нет».
3. **Дрейф yaw.** 60 с непрерывного вращения: сколько градусов уехало.
   Норма для телефона — единицы градусов в минуту; всё, что хуже,
   требует якоря (§1.2, §3.1).
4. **Синхронизация двух телефонов без сети.** Хлопок или chirp, запись на
   обоих, кросс-корреляция → субмиллисекундная синхронизация. Нужна для
   ритм-игр и для честного замера задержки.
5. **Свет вместо часов.** Вспышка на экране второго телефона, пойманная
   камерой очков, даёт привязку «кадр ↔ событие» точнее любого таймера.

Правило skill'а: без этих цифр статус остаётся `not device-tested`, даже
если все синтетические тесты зелёные.

## 7. Тупики

Проверенные или предсказуемые — не тратьте вечер.

- **OpenCV.js на главном потоке каждый кадр.** 8 МБ wasm, readback,
  секунды на первом кадре. Если очень нужно — Worker, маленький кадр,
  редкая частота, прогрев.
- **60 Гц позы через RTDB/Firestore.** Лимиты и задержка, а не «немного
  медленнее».
- **Интегрирование акселерометра в позицию.** Двойной интеграл шума =
  метры дрейфа за 10 с. Только как признак шага, не как позиция.
- **IR-метки без снятия IR-cut фильтра.** Телефонная камера почти не видит
  850 нм; «дешёвый инфракрасный трекинг» так не получается.
- **Точный eye-tracking фронталкой в картоне.** Только моргание (§1.6).
- **Цвет как единственный ID.** Детская комната = ложные срабатывания.
- **WebXR на картонном классе.** Не тот класс устройства; своя стерео-схема
  честнее.
- **Сырой магнитометр в вебе.** За флагом; для магнита нужен ESP32.
- **Роллинг-шаттер и ШИМ экрана как прецизионные часы.** Годится для
  «примерно», не для синхронизации.

## 8. Три спайка на один вечер

Каждый — отдельная ветка, не трогающая игру, с числами на выходе.

### S1. Тег → 6DoF (`synthetic` → `device-tested`)

- Детектор тега на 480–640 px в Worker, поза из гомографии.
- Приёмка: неподвижный тег 10 с → std `t` ≤ 3 мм, std углов ≤ 0,5°;
  известное расстояние 0,5/1/2 м → ошибка ≤ 3 %; 10 Гц на среднем
  телефоне без просадки рендера; декод при наклоне до 50°.
- Провал, если < 5 Гц или дрожание > 1 см — тогда двухъярусная схема
  обязательна.

### S2. Внешняя камера + fusion

- Старый телефон на штативе, тег на очках, поза по WebRTC.
- Приёмка: наклон головы вперёд на 30 см отражается в мире с ошибкой
  ≤ 5 см; нет телепорта при потере кадра; деградация
  `vision → gyro-only → held` видна в подготовке.
- Провал, если задержка коррекции > 300 мс — тогда только «медленный
  якорь», без позиции в реальном времени.

### S3. Датчик на ноге / chaperone

- ESP32 + MPU6050 на ноге, шаг → скорость; или VL53L1X на очках.
- Приёмка: 100 шагов, ложных ≤ 5 %, задержка ≤ 100 мс, 20 минут без
  отвала BLE; предупреждение о стене срабатывает за 40–60 см.
- Провал по BLE — значит провод/телефон в кармане, а не ESP32.

## 9. Семена механик (сенсор → игра)

- **Ретрорефлектор + фонарик** → «свети и ищи»; мир виден только там, куда
  попал луч.
- **Компас врёт** → сюжет: в комнате есть «место, где север сломан».
- **Дунуть в микрофон** → задуть свечу, надуть парус, остудить лаву.
- **Крик** → разбить стекло, разбудить существо, измерить «смелость».
- **Моргание** → переключение миров (моргнул — увидел духов).
- **Коврик** → граница площадки = граница мира; сошёл — упал.
- **Метка на руке** → реальный предмет становится инструментом.
- **ToF** → «горячо/холодно» без экрана; сонар в темноте.
- **Экран второго телефона как портал** → окно в другую комнату.
- **Второй игрок на пульте** → асимметричная игра: один в очках, второй
  «режиссёр», который двигает мир.
- **Синхронизация по хлопку** → ритм-игра на двух телефонах без сервера.
- **Внешняя камера** → «наклонись и загляни» вместо «нажми кнопку».

## 11. Что записать в контракт, если берёте идею в игру

1. Какой дефицит из §0 закрывается и каким числом это проверяется.

5. Что не проверялось на устройстве (честный `not device-tested`).
6. Какая механика **не** работает без покупки — чтобы не обещать её в MVP.
